# limo_workspace AI 작업 지침

- 이 저장소는 실차 전용이다. 저장소 루트가 LIMO 워크스페이스의 `src/`이므로 패키지 경로 앞에 `src/`를 다시 붙이지 않는다. 실차에서 colcon 빌드를 안내할 때는 해당 워크스페이스 루트를 기준으로 한다.
- 패키지 경로를 바꿀 때 package.xml, 설치 경로, 런치의 패키지 조회와 기존 호출 방식을 함께 확인한다. Nav2 또는 센서 설정 변경 전 실제 런치가 선택하는 YAML과 토픽·TF·QoS를 추적한다.
- 기존 미커밋 변경과 다른 작업자의 파일을 보존한다. 커밋·푸시·PR·삭제·작업트리 변경은 사용자 승인 범위를 따른다.
- [시작 안내](START_HERE.md)에서 관련 문서를 선택하고 현재 브랜치의 실제 코드와 대조한다.

## 1. 코드와 실행 환경 확인

- 저장소 상태를 조사할 때는 현재 브랜치·커밋·미추적 파일을 함께 확인한다. GitHub의 소스와 로봇의 설치본을 비교할 때는 양쪽 버전과 로봇에서 소싱한 워크스페이스를 기록한다. 로봇 접근이 없으면 확인한 로컬 범위를 명시한다.
- 메인 소스 폴더는 `limo_capstone_ros/`, ROS 패키지명은 `limo_capstone`이다. 빌드나 런치 인식 문제에서는 package.xml, setup.py의 설치 대상, 소싱 순서, `ros2 pkg prefix limo_capstone` 출력을 확인한다.
- 주행 문제는 실행한 런치와 인자에서 시작한다. 실제 로드된 YAML, remapping, 센서 발행 주기, TF의 부모·자식 프레임, 명령을 발행하고 받는 노드를 차례로 추적한다. 노트북과 본체에 나눠 실행했다면 각 장치가 맡은 노드를 적는다.

## 2. 실차 시험과 증거

시험마다 커밋 또는 배포본 식별 정보, 런치 명령과 인자, 센서 구성, 모터 상태, 기대 동작, 관찰 결과, 로그 또는 rosbag 위치를 남긴다. 빌드·단위 시험, 실차 정지 관측, 모터 잠금 후 수동 이동, 실제 주행 가운데 수행한 조건을 표시한다.

속도 명령 경로나 장애물 처리 변경은 입력 끊김, 오래된 오도메트리, 중지 후 명령 재발행 등 해당 변경과 관련된 실패 조건을 살핀다. 구동 시험 전에 현장 통제와 정지 수단을 확인한다. 중단된 시험은 중단 시점, 관찰한 상태, 복구한 자료와 원인 규명 여부를 기록한다.

## 4. 여러 AI가 작업할 때

담당 브랜치·파일·검증 범위를 정하고 기존 작업트리와 작업 결과를 먼저 확인한다. 공통 문서를 동시에 수정 중이면 별도 변경 제안에 대상 문서, 이유, 수정 문안, 근거 커밋·시험 기록, 미해결 사항을 적는다. 통합할 때는 최신 코드와 대조하고 충돌이 남은 항목은 근거와 함께 인계한다.

다른 AI에게 전달하는 프롬프트에는 목표, 읽을 문서와 소스, 허용된 변경 범위, 실차 접근 여부, 완료 조건을 넣는다. 모델 추천은 사용자가 이용할 수 있는 모델과 직접 지정한 설정을 우선한다. 선택지가 있으면 1~3순위에 에이전트·모델명·추론 강도·이유를 적는다. 고장 원인 분석이나 제어 경로 변경에는 깊은 추론을, 범위가 분명한 문서 수정이나 반복 검사에는 사용량 효율을 고려한다. 모델을 바꿀 때는 현재 변경과 시험 결과를 함께 넘긴다.

### 커밋 메시지·PR·이슈 작성

- 저장소 템플릿이 있으면 그 구조를 우선한다. 제목과 본문은 한국어로 작성하고, 커밋 유형, 패키지명, 명령, 오류 메시지 등 정확한 식별이 필요한 표현은 원문을 유지한다.
- 커밋 메시지는 `type(scope): 한국어 요약` 형식을 사용한다. 범위가 명확하면 scope를 생략할 수 있다. 예시: `fix(nav2): 정적 지도 주행에 LIMO 설정 적용`.
- PR 제목은 변경 목적을 한 줄로 요약한다. 본문에는 변경 이유, 주요 변경 사항, 검증 방법과 결과를 적고 관련 이슈가 있으면 연결한다.
- 이슈 제목에는 증상이나 작업 목표를 적는다. 버그 본문에는 환경, 재현 절차, 기대 동작, 실제 동작을 적고, 기능 요청에는 배경, 요청 사항, 완료 조건을 적는다.
